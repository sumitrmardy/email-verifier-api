# 计费与批量

## 按什么收费

每个**得出结论**的地址计费一次 —— 包括 `undeliverable` 和 `unknown`。
这两类同样消耗了验证过程，而且一个被确认的坏地址，正是你付费想得到的结果。

没有按运行次数的收费，所以只验证一个地址的运行就只花一个地址的钱。

单价按你的 Apify 套餐分层，并会随时间调整，因此不在这里写死以免过期：
**[查看当前价格](https://apify.com/sumitr_mardy/email-verifier/pricing)**。

### 两种白花钱的情况

**重复地址会计费。** 调用前先去重。本仓库所有模板都做了，并且是忽略大小写的 ——
`John@x.com` 和 `john@x.com` 是同一个邮箱。

**重复验证没变化的行也会计费。** T1 模板只读取 `status` 列为空的行，
所以定时运行只会处理新线索，而不是把整张表重新计费一遍。

结论值得缓存。`score` 是结论的纯函数，所以存下来的结果依然有效。
但地址会过期 —— 人会离职 —— 所以按适合你名单的周期重新验证，
而不是每次发送前都验一遍。

## 批量

**一次调用，多个地址。** 绝不要一个地址一次调用：更慢，而且单价完全一样。

同步运行必须在 **300 秒**内完成。超过这个时间连接会被切断 ——
而运行在 Apify 那边还在继续，并且照常计费。所以批量大小不是性能微调，
而是"拿到结果"和"为看不到的结果付钱"之间的分界线。

### 真正决定速度的是什么

不是地址数量，是**不同域名的数量**。

DNS 查询和全收域名探测按域名缓存 24 小时，而且地址会按域名分组，
一个 SMTP 会话可以连续发多条 `RCPT TO`。所以：

- 1,000 个地址分布在 50 个域名 —— 快。主要工作量只有 50 次探测。
- 1,000 个地址分布在 900 个域名 —— 慢得多。几乎每个地址都要单独解析、单独建连。

从 CRM 导出的 B2B 名单接近第一种。消费者注册名单接近第二种。
**用和你自己类似的名单去实测** —— 别人名单上测出的数字说明不了什么。

### 怎么测

`npm run smoke` 会对 fixture 名单计时，并给出能塞进一半上限的批量大小。
或者用你自己的名单：

```bash
APIFY_TOKEN=... node examples/node/verify.mjs $(head -50 your-list.txt | tr '\n' ' ')
```

取"每个地址多少毫秒"，目标是让一批在 **150 秒**内完成 —— 也就是上限的一半，
这样遇到一个慢域名也不会整批丢掉。

```
批量大小 ≈ 150,000 / (每个地址的毫秒数)
```

**从 100 开始。** 对多数名单都宽裕，本仓库模板用的就是这个值。
实测之后再往上调，不要凭感觉调。

### 一个参考值

在 Actor 自己的 166 个地址标注集上、经由 relay：总计约 40 秒，
每个地址约 240 毫秒，涉及 69 个不同域名。地址与域名之比 2.4:1 属于
**域名密度异常高**的情况 —— 真实客户名单基本都会比这个快。

### 超出一批的量

名单大到任何单次同步调用都装不下时，不要硬提批量大小直到报错。
改用异步：启动运行、等待完成、再取 dataset。完整示例：
[`examples/batch-large-list/`](../examples/batch-large-list)

异步没有 300 秒上限，而且你的连接断了运行也不会停。

## 并发

`concurrency`（1–50，默认 15）是并行的 SMTP 会话数。因为地址按域名分组，
它实际含义是"同时处理多少个域名"。

调高它对域名分散的名单有效，对集中在少数域名的名单没用 ——
并发数不可能超过你实际有的域名数。数值过高还会被邮件服务器限流，
结果变成 `unknown/greylisted`，等于多付一次验证的钱。

15 是合理默认值。域名分散的名单可以用 25–30。再往上请实测，不要假设。
